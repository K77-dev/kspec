## Visão Geral

Executar os 7 cenários de teste definidos na techspec para validar que o sistema de validação de skills empresariais funciona corretamente em todas as situações: instalação inicial, validação de hashes, atualização, fallback offline, bloqueio, remoção de skills obsoletas e descoberta de novas skills.

## Subtarefas

- [ ] 5.1 Cenário: Lock local ausente + rede OK — Remover `enterprise-skills-lock.json`, executar uma skill kspec e verificar que skills são instaladas e lock é criado
- [ ] 5.2 Cenário: Lock local presente + hashes válidos — Executar uma skill kspec e verificar mensagem `✓ Skills empresariais validadas` sem downloads
- [ ] 5.3 Cenário: Lock local presente + hash divergente — Alterar o `computedHash` no lock local, executar uma skill kspec e verificar que a skill é reinstalada
- [ ] 5.4 Cenário: Rede indisponível + skills instaladas — Remover o cache `.claude/.enterprise-skills-cache/`, simular falha de rede (URL inválida no lock), executar skill e verificar aviso mas execução permitida
- [ ] 5.5 Cenário: Rede indisponível + skills ausentes — Remover cache, lock local e arquivos das skills, simular falha de rede, executar skill e verificar que é bloqueada com mensagem de erro
- [ ] 5.6 Cenário: Skill removida do remoto — Adicionar uma skill fictícia ao lock local que não existe no `skills-lock.json` remoto, executar validação e verificar que é removida localmente
- [ ] 5.7 Cenário: Nova skill adicionada ao remoto — Verificar que quando o `skills-lock.json` remoto tem uma skill não presente localmente, ela é instalada automaticamente

## Detalhes de Implementação

Consultar a seção **"Abordagem de Testes > Testes Unitários"** da techspec.md para a tabela completa de cenários e verificações esperadas.

**Para cada cenário:**
1. Preparar o estado inicial (manipular lock file, cache, arquivos de skills conforme necessário)
2. Executar a ação (invocar uma skill kspec ou bootstrap)
3. Verificar o resultado (mensagens exibidas, estado do lock file, presença/ausência de arquivos)
4. Restaurar o estado original após o teste

**Cenários de teste detalhados:**

| # | Estado inicial | Ação | Resultado esperado |
|---|---|---|---|
| 5.1 | Lock ausente, rede OK | Executar skill kspec | Skills instaladas, lock criado, mensagem de instalação |
| 5.2 | Lock presente, hashes OK | Executar skill kspec | `✓ Skills empresariais validadas`, sem downloads |
| 5.3 | Lock com hash alterado | Executar skill kspec | Skill reinstalada, lock atualizado, mensagem de atualização |
| 5.4 | Sem cache, URL inválida, skills presentes | Executar skill kspec | `⚠` aviso, skill executa normalmente |
| 5.5 | Sem cache, URL inválida, sem skills | Executar skill kspec | `✗` erro, skill NÃO executa |
| 5.6 | Lock com skill fictícia | Executar validação | Skill fictícia removida do projeto e do lock |
| 5.7 | Lock sem skill que existe no remoto | Executar validação | Nova skill instalada automaticamente |

## Critérios de Sucesso

- Todos os 7 cenários executados e passando
- Mensagens de feedback corretas em cada cenário (✓, →, ⚠, ✗)
- Lock file atualizado corretamente após cada operação
- Symlinks criados/removidos conforme esperado
- Fallback offline funciona (permite com skills instaladas, bloqueia sem)
